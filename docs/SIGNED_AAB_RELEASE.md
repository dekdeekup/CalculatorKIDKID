6. Do not save secrets into tracked Gradle files. 7. Verify the signed output using `jarsigner -verify -verbose -certs <signed.aab>`. Require an actual signed-entry verification result, not only exit code zero (an unsigned JAR may also exit successfully). Inspect the signer with `keytool -printcert -jarfile <signed.aab>` and compare its fingerprint with the independently recorded owner upload certificate. Explain any trust-chain warning rather than treating a self-signed upload certificate as publicly CA-certified. Validate bundle structure with an appropriate verified bundletool version and inspect package/version/SDK/permissions/languages. Record tool versions, SHA-256, certificate fingerprint and verification outputs.
8. Test installable APKs derived from the signed AAB using bundletool and an owner-authorized **test** signing configuration, or later through an explicitly authorized Play testing workflow. An AAB is not directly installable with `adb install`. If the upload and Play app-signing certificates differ, an APK locally signed with the upload key does not prove update compatibility with Play-distributed APKs. Verify upgrade/data preservation with the appropriate distribution signature. Keep debug and release-install data-loss implications explicit.
9. Deliver the signed AAB, complete matching source, test APK as appropriate, checksums, signing/verification record and completed acceptance report. Exclude keystores, passwords, caches and machine-local configuration from the source ZIP. Preserve the original approved specifications.
10. Stop before any Play upload/submission, production rollout, permanent key creation or signing-key enrollment unless the owner has explicitly authorized that action. Internal/closed testing and production approval are separate milestones and must never be represented as completed because local builds pass.

A successful build, a signed bundle, a device-test pass, a Play upload and Play approval are different facts. Record each independently; none implies the others.
